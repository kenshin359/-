# Libetee 参謀室 ── 組織設計書

> 社長（経営）と 参謀（Claude）で会社を動かすための「作戦本部」の設計図。
> 目的は明快 ── **月商1億 → 10億を、勘ではなく数字で達成する組織をつくる。**

---

## 0. 体制の全体像

```
                        ┌─────────────┐
              社長 ─────│    参 謀     │──── 経営判断に必要な数字だけを上げる
           （意思決定）  │ (Claude/司令塔) │
                        └──────┬──────┘
                    指示 ↓            ↑ 報告
             ┌──────────────┴──────────────┐
       ┌─────┴──────┐                 ┌─────┴──────┐
       │  予想チーム   │  ←── ズレを戻す ──  │  分析チーム   │
       │ (立案・攻め)  │  ── 見込みを渡す ──→ │ (検証・守り)  │
       └────────────┘                 └────────────┘
                    共通の土台：kintone 売上日報 ＋ イベント暦
```

- **社長**：意思決定者。数字を見て「やる／やめる／もっと張る」を決める。
- **参謀（私）**：司令塔。2チームを動かし、判断に必要な数字だけを社長に上げる。雑音は上げない。
- **予想チーム**：攻め。次にいくら売れるか、そのためにいくら広告を張るかを立案する。
- **分析チーム**：守り。予想と実績のズレを解剖し、取りこぼしの原因と打ち手を出す。

この2チームは**実体として動きます**（`.claude/agents/` のサブエージェント）。
飾りの組織図ではなく、社長が「予想チーム、次のマラソンいくらいく？」と聞けば動く実働部隊です。

---

## 1. なぜ「予想」と「分析」を分けるのか

同じ人間が予想と検証を両方やると、「自分の予想を正当化する分析」になって精度が上がりません。
**立てる人と、答え合わせする人を分ける。** これが数字で伸ばす組織の最小構成です。

| | 予想チーム | 分析チーム |
|---|---|---|
| 役割 | 未来を数字で言い切る | 過去を数字で解剖する |
| 問い | 「次いくら売れる？いくら張る？」 | 「なぜズレた？次どう埋める？」 |
| 出力 | 売上予想(P25/本命/P75)＋広告配分 | 原因特定＋打ち手＋担当割り |
| 道具 | `npm run forecast` / `calendar` | `npm run analyze` / `out/daily.json` |
| 姿勢 | 攻め（機会を最大化） | 守り（無駄と取りこぼしを潰す） |

## 3. 作戦のまわし方（PDCAの週次リズム）

```
   月曜  ──  予想チーム：今週・次イベント日の見込みと広告配分を出す（Plan）
   平日  ──  実行：社長・現場が広告とイベント準備を回す（Do）
   日次  ──  売上日報を kintone に入力（売上・広告費・イベント名）
   金曜  ──  分析チーム：実績を解剖、予想とのズレの原因と打ち手（Check）
   金曜  ──  参謀：来週の作戦に反映し社長へ報告（Act）
```

- **イベント2週間前**：予想チームが「弾込め会議」の材料を出す（在庫・広告前倒し・クーポン設計）。
- **イベント翌日**：分析チームが即日で「取れた／取り逃した」を出し、次イベントに活かす。

## 4. 数字の握り方（KPI）

**北極星：月商。** ただし月商だけ見ても打ち手は出ないので、下記に分解して握ります。

- **月商** ＝ 平常日売上 ＋ イベント日売上
  - 月商1億 → 1日平均 **約333万** ／ 月商10億 → 1日平均 **約3,300万**
- **平常日ベースライン**（底上げの対象）／ **イベント日リフト率**（イベント日は平常日の何倍か）
- **ROAS**（売上 ÷ 広告費、既定目標 **5.0**）… 効率の生命線。低いチャネルは広告かCVRに穴
- **チャネル別**：どこが伸びしろか。1チャネル依存はリスク、複数チャネルで面を取る
- **CVR / アクセス**：アクセスはあるのに売れない(=CVR/価格/在庫) か、そもそも露出が無い(=広告) か

これらは `npm run analyze` が毎回自動で出します。**会議は数字が出た状態から始める。**

## 5. 月商1億 → 10億 ロードマップ

| フェーズ | 目安月商 | 主戦場 | この時期にやること |
|---|---|---|---|
| **Phase 1：土台を固める** | 〜1億 | 楽天・Amazon | 日報を毎日入れる／広告費を必ず記録／イベント日を暦に登録。**数字が溜まらないと予想は当たらない。まずここ。** |
| **Phase 2：イベントで跳ねる** | 1〜3億 | 楽天SALE・プライムデー | イベント日リフト率を上げる（在庫・広告前倒し・クーポン）。予想の的中と広告ROASの両立。 |
| **Phase 3：面を広げる** | 3〜10億 | 6チャネル＋新規 | TikTok/Qoo10/BASE を伸ばしチャネル分散。平常日ベースライン自体を底上げ。 |

**いま最優先なのは Phase 1。** 予想の精度も広告の最適化も、日々の正確な入力があって初めて効きます。

## 6. 使い方（社長がすぐ動けるコマンド）

```bash
npm run calendar    # 次にどのイベントが来るか（楽天/Amazonの暦）
npm run analyze     # 売上・広告費・ROAS・イベント日vs平常日を出す（会議の前に必ず）
npm run forecast    # 次のイベント日にいくら売れるか（弱気/本命/強気）
```

チームを呼ぶときは私（参謀）に一言：
- 「**予想チーム**、次のスーパーSALE いくらいく？広告いくら張る？」
- 「**分析チーム**、先月なんで楽天が落ちた？次どう埋める？」

私が2チームを動かし、社長には**判断に必要な数字と選択肢だけ**を上げます。

## 7. 約束事（安全）

- 認証情報（`.env`：kintone のユーザー/パスワード/APIトークン）は**コードにもドキュメントにも一切書かない**。全て環境変数から読む。
- 予想は必ず**実績 × 倍率**で説明できる数字にする。願望値は出さない。
- 分析は「頑張ろう」で終わらせない。**原因 → 打ち手 → 誰がいつまでに**をセットで出す。
