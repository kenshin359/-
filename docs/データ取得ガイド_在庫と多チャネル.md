# データ取得ガイド ── 在庫と多チャネル（次の一手）

> 目的：楽天と同じ分析（月商推移・イベント別倍率・下落要因）を **Amazon・自社サイト** にも広げ、
> かつ **在庫** を分析の第一級データとして組み込む。

---

## 0. なぜ在庫が要るか（10月の教訓）

2025年10月の楽天▲44%の根本原因は **在庫切れ**。因果は
**在庫切れ → 売る物が無い/広告停止 → アクセス減 → 売上減**。
「集客の谷」は結果で、引き金は欠品。**在庫の確保はイベント成功の前提条件。**
→ 売上・広告に加え「在庫（欠品）」を毎日記録すれば、下落を事前に防げる。

---

## 0.5. 在庫切れの機会損失（実測・分析の締め）

既存の楽天データで在庫切れ期の損失を金額化：
- 在庫切れ前3か月(2025/7-9)の日商 = ¥879,537/日
- 2025/10 実績¥14.4M（平常運転なら¥27.3M → ▲¥12.9M）
- 2025/11 実績¥15.1M（平常運転なら¥26.4M → ▲¥11.3M）
- **2か月合計の機会損失（推定）：¥1,700万〜¥2,400万**

→ **在庫確保はイベント広告より先の“最優先投資”。** 画像：`sheets/img_loss.png`。
SKU（カラー）別在庫があれば、どの色でいくら失ったかを正確に確定できる。

## 0.8. 楽天でカラー別（バリエーション）在庫を数値管理する

| # | データ | RMSの場所 | 粒度 |
|---|---|---|---|
| ① | **項目選択肢別 在庫**（★カラー別はここ） | RMS →「商品管理 > 商品ページ一括編集(CSV)」の在庫タイプ2＝項目選択肢別在庫／新在庫管理画面 | SKU×カラー/サイズ別 在庫数 |
| ② | 受注データ（販売実績） | RMS →「受注管理 > 受注データダウンロード(CSV)」 | 注文ごとの項目選択肢(カラー)＋数量 |
| ③ | 売上・アクセス・転換率 | データ分析（売上・アクセスレポート）※取得済 | 店舗日次 |

CSVの `商品管理番号 / 項目選択肢(横=カラー) / 項目選択肢(縦=サイズ) / 在庫数` がカラー別在庫そのもの。
**RMSは「今の在庫」しか持たない** → ①を毎日CSVダウンロードして日付を付けて保存すると
「カラーX が ○/○ に欠品 → その日の売上」が数値で紐づく。②と突き合わせれば欠品カラーの損失も出る。

|---|---|---|---|---|

## 2. 在庫を「日次」で残す2ルート

在庫はその瞬間のスナップショット。日々の売上と突き合わせるには日次で残す仕組みが必要。

### ① 簡易（今日から）── 欠品フラグ手入力
- 毎朝、**主要SKUの「欠品有/無」フラグ**を日報に記録（在庫数まで不要、まず有無だけでOK）。
- 既存の kintone スキーマに `在庫切れフラグ` を提案済み。効果測定シートにも列追加可。
- これだけで「欠品した日 vs 平常日」の売上差＝機会損失が即見える。

### ② 本格（自動）── API連携
- 楽天RMS API／Amazon SP-API／Shopify Admin API で **毎日在庫数を自動取得し SKU×日 で蓄積**。
- 認証情報はすべて `.env`（環境変数）。コードには一切書かない。
- 参謀が取得スクリプトを実装可能。

---

## 3. Amazon・自社サイト分析の進め方

1. 上表の **売上CSV** を楽天と同じ粒度（日次・SKUまたはチャネル別）で書き出す。
2. 参謀が楽天と同じ分析（月次推移・イベント別倍率・アクセス連動・下落要因）を生成。
3. 在庫（欠品フラグ）を重ねて「欠品による機会損失」を金額化。
4. 3チャネル横断で「どのチャネルの、どのイベントに、いくら広告を張るか」を予想チームが最適配分。
