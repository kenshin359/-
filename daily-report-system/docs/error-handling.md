# エラー対応マニュアル

各エラーの「原因 → システムの挙動 → 対処」をまとめます。
実装箇所は `lib/httpRetry.js`（共通リトライ）と各 `scripts/`・n8n ノードです。

---

## 1. Kintone API エラー

| 状況 | システムの挙動 | 対処 |
|------|----------------|------|
| 401/403（トークン不正・権限不足） | 即エラー停止（リトライしない） | APIトークンと権限、`.env` を確認。アプリ更新済みか確認 |
| 400（クエリ不正・unique重複） | 即エラー。unique重複は「重複送信防止」として意図的 | クエリ／フィールドコードを確認 |
| 429 / 5xx / ネットワーク | 指数バックオフで最大4回再試行（2s,4s,8s,16s） | 自動回復。続く場合は kintone 稼働状況を確認 |

## 2. Claude API エラー

| 状況 | 挙動 | 対処 |
|------|------|------|
| 401（キー不正） | 即停止 | `ANTHROPIC_API_KEY` を確認 |
| 429（レート制限） | `Retry-After` 優先で再試行、無ければ指数バックオフ | 自動回復。頻発時はモデル/頻度を見直し |
| 5xx / タイムアウト | 再試行（最大4回、n8n は timeout 120s） | 自動回復 |
| 空応答 | エラーにして `gen_status=生成失敗` を記録 | 再実行。プロンプト・入力量を確認 |

## 3. LINE API エラー

| 状況 | 挙動 | 対処 |
|------|------|------|
| 401（トークン不正） | 即停止、`line_result=送信失敗` | チャネルアクセストークン再発行 |
| 400（宛先不正・本文空） | 即停止 | `LINE_TARGET_*` ID を再確認 |
| 429（無料通数超過・レート） | 再試行、続けば失敗記録 | プラン見直し／送信頻度削減 |
| 文字数超過 | **送信前に 4,800字で自動分割**＋5吹き出し単位に分割 | 追加対応不要 |

## 4. JSON パースエラー（Claude 応答）

- ` ```json ` フェンスや前後の文章を許容して抽出（`parseJsonFromModel`）。
- それでも失敗した場合：`gen_status=生成失敗`、`error_log` に生出力の先頭を保存し、**LINEは送らない**。
- 対処：`error_log` を見てプロンプトを調整。`prompts/daily-report-system-prompt.md` の「JSONのみ出力」指示を再確認。

## 5. 日報0件

- ワークフロー①：LINE に「本日の日報提出はありませんでした」を通知し、記録レコードを残して正常終了。
- 対処：`提出状況=提出済み` になっているか、対象日が正しいかを確認。

## 6. 未提出（一部スタッフ）

- 集計対象は「提出済み」のみ。未提出者は Claude の `ai_analysis` で「報告不足」として言及される設計。
- 運用対処：Kintone の条件通知やリマインドで未提出者に催促。

## 7. 重複実行

- **AI経営日報アプリの `target_date` を unique 設定**（Kintone側の一次防御）。
- スクリプト側：`findAiReportByDate` で既存チェックし、あればスキップ（`runPipeline.js` / `saveAiReport.js`）。
- 結果：同じ日に2回走っても、2回目は保存もLINEもしない → **重複送信防止**。

## 8. LINE 文字数超過

- `lib/line.js` の `splitForLine` が 4,800字ごとに改行位置で分割 → 5吹き出しずつ複数リクエスト。
- n8n 側も「応答を整形」ノードで同等の分割を実施。

## 9. レート制限（共通）

- `lib/httpRetry.js` が 429 と 5xx を指数バックオフで再試行。`Retry-After` を尊重。
- それでも回復しなければエラーを記録して停止（無限リトライしない）。

## 10. ネットワーク障害

- `fetch` 失敗（接続断など）は最大4回、2s→4s→8s→16s で再試行。
- Git push など運用スクリプトも同様のバックオフ方針。

---

## Webhook 保護（ワークフロー②）

- n8n の Webhook ノードの後段で `x-webhook-secret` ヘッダを `WEBHOOK_SECRET` と照合。不一致は 401。
- kintone Webhook は任意ヘッダを付けられないため、次のいずれかで保護：
  1. n8n 側でボディ内の固定トークン（例 `body.token`）を検証する（IFノードの条件を差し替え）。
  2. Webhook URL 自体を推測困難な長いパスにする（`path` をランダム文字列に）。
  3. 中継サーバ（Cloud Functions 等）でヘッダ付与してから n8n へ転送。
- **秘密情報はログに出さない**：本システムは APIキー・トークンをログ出力せず、必要時のみ `mask()` で先頭数文字のみ表示。

## 監視のすすめ

- AI経営日報アプリで `生成ステータス=生成失敗` または `LINE送信結果=送信失敗` に**条件通知**を設定。
- n8n は `Settings → Error Workflow` を作り、失敗時に管理者へ通知するワークフローを紐付けると安心です。
